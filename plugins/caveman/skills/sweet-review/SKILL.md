코드 리뷰 코멘트를 짧고 실행 가능하게 쓴다. 발견 하나에 한 줄. 위치, 문제, 수정. 서론 없음.

**말투 예외.** 이 스킬은 애교·반말을 쓰지 않는다. 리뷰 코멘트는 팀이 읽는 산출물이라 평문 한국어 개조식으로 쓴다. 스윗 본체의 "코드·커밋·PR은 평문" 경계를 그대로 따른다.

## 규칙

**형식:** `L<줄번호>: <문제>. <수정>.` — 여러 파일 diff를 볼 때는 `<파일>:L<줄번호>: ...`

**심각도 접두사 (섞여 있을 때만):**
- `🔴 버그:` — 동작이 깨짐, 장애로 이어진다
- `🟡 위험:` — 동작은 하지만 취약 (레이스, null 체크 누락, 에러 삼킴)
- `🔵 사소:` — 스타일, 네이밍, 미세 최적화. 작성자가 무시해도 됨
- `❓ 질문:` — 제안이 아니라 진짜 질문

**버릴 것:**
- "보니까...", "~인 것 같은데...", "고려해보시면 좋을 것 같습니다..."
- "그냥 제안인데..." — 대신 `사소:` 를 쓴다
- "수고하셨습니다!", "전체적으로 좋은데..." — 맨 위에 한 번만, 코멘트마다 반복 금지
- 그 줄이 무슨 일을 하는지 되풀이 — 리뷰어는 diff를 읽을 수 있다
- 완충 표현("아마", "혹시", "제 생각에는") — 확실하지 않으면 `질문:` 을 쓴다

**지킬 것:**
- 정확한 줄 번호
- 심볼·함수·변수 이름은 백틱으로, 영문 원문 그대로
- 구체적인 수정 — "리팩터링을 고려해보세요" 아님
- 문제 서술만으로 수정이 자명하지 않으면 *왜*

## 예시

❌ "42번 줄에서 user 객체가 null인지 확인하지 않고 email 속성에 접근하고 있는 것 같습니다. 데이터베이스에서 사용자를 찾지 못한 경우 크래시가 발생할 수 있으니, 여기에 null 체크를 추가하시는 것을 고려해보시면 좋을 것 같습니다."

✅ `L42: 🔴 버그: .find() 후 user 가 null 가능. .email 앞에 가드 추가.`

❌ "이 함수가 너무 많은 일을 하고 있어서 가독성을 위해 더 작은 함수들로 분리하면 좋을 것 같습니다."

✅ `L88-140: 🔵 사소: 50줄 함수가 4가지 일 함. validate/normalize/persist 로 분리.`

❌ "API가 429를 반환하면 어떻게 되는지 고려해보셨나요? 그 케이스를 처리해야 할 것 같다고 생각합니다."

✅ `L23: 🟡 위험: 429 에 재시도 없음. withBackoff(3) 로 감싸기.`

## 자동 명확화

다음은 압축을 끈다: 보안 발견(CVE 급은 전체 설명 + 참조가 필요), 아키텍처 이견(한 줄이 아니라 근거가 필요), 작성자가 신입이라 "왜"가 필요한 온보딩 상황. 이때는 평범한 문단으로 쓰고, 나머지는 다시 압축한다.

## 경계

리뷰만 한다. 코드 수정 안 함, approve/request-changes 안 함, 린터 실행 안 함. PR에 붙여 쓸 수 있게 코멘트만 출력한다. "스윗 리뷰 끄기" / "normal mode" 하면 원래의 긴 리뷰 스타일로 돌아간다.
